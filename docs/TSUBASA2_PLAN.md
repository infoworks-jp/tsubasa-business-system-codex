# つばさ2 開発計画

- 作成日: 2026-07-29
- 前提: つばさ1は保存用として維持し、既存の業務・実データ・公開環境を変更しない。
- 根拠: [つばさ2事前監査](TSUBASA2_AUDIT.md)
- 目標: 小規模飲食店が、原本から確認・確定・集計・経営判断までを安全に行える月額サービスを作る。

## 開発方針

つばさ2は、新しい非公開リポジトリ（候補: `tsubasa-business-system-v2`）で開始する。つばさ1に新機能を積み重ねない理由は、現行に匿名許可RLS・未接続の認証・原本未保存の取込処理が混在しており、販売用の土台にすると既存の調査・修正が同時に必要になるためである。

つばさ1からは、商品マスター、価格履歴、入力検証、画面部品、テストの考え方だけを、実データなしで選択的に移植する。DB、RLS、OCR、取込、確定、品質画面はつばさ2で新規に実装する。

## つばさ2 MVP

MVPは「画像をAIで読むこと」ではなく、「根拠を残して、間違えずに売上を確定できること」を最優先にする。

### MVPに含めるもの

1. 組織、店舗、利用者、役割（所有者・入力者・確認者・閲覧者）
2. 店舗単位で完全に分離したSupabase RLS
3. 画像、PDF、CSV、手入力の原本登録
4. 原本の不変保存、SHA-256、MIME、サイズ、登録者、保存日時、重複候補
5. 原本に紐づく取込下書きと人による訂正
6. 確認、確定、差戻し、訂正新版、操作監査
7. 日本時間、店舗ごとの営業日境界、月曜予定休業と例外営業
8. 日別、商品別、時間帯別の集計とD/P/T差額表示
9. 基本ダッシュボード（売上、客数、客単価、商品構成、曜日別）
10. 検索、状態表示、短時間有効URLによる原本閲覧
11. 自動バックアップの記録と、匿名化データによる復元試験
12. 取込・確定・集計を対象にした自動テストとCI

### MVPから外すもの

次の機能は、上記の確定フローが実データで安全に動いた後に追加する。

- OCRの自動確定
- 複数のAIを同時に使うOCR
- 通帳照合
- 人件費、原価、利益分析
- AI経営改善提案
- Facebook、Instagram投稿案
- 会計ソフト、キャッシュレス、在庫連携
- 複数店舗横断の比較
- 顧客向け請求・契約・決済画面

OCRはMVPで「候補値を作る補助」として導入可能だが、確定を自動化しない。外部OCRは店舗の明示選択、送信先・費用・保存方針の同意、1回の実行、再実行履歴を必須にする。

## 10個以内の小さなPR計画

| PR | 目的 | 主な成果 | 完了条件 |
|---|---|---|---|
| 1 | 開発の安全網 | つばさ1のCI、秘密情報検査、テスト実行手順、変更テンプレート | 既存コードを変えず、install・test・typecheck・lint・buildがPRで実行される |
| 2 | つばさ2の新規土台 | 新しい非公開リポジトリ、pnpm、Next.js、テスト用の人工データ | つばさ1とDB・環境変数・Storageを共有しない |
| 3 | 認証と店舗分離 | Supabase Auth、organizations、stores、store_members、RLS | 匿名アクセス不可。別店舗の読み書きを自動テストで拒否 |
| 4 | 原本台帳と保存 | 非公開Storage、SHA-256、重複候補、不変保存、短時間有効URL | 原本を削除・上書きできず、同一ファイル候補を検出 |
| 5 | 取込下書きと確認 | CSV/画像/手入力の下書き、原文、原本位置、確認・差戻し | 訂正前後と確認者を保存し、未確認値は確定できない |
| 6 | 確定と営業日 | JST、営業時間境界、月曜予定休業、例外営業、確定版・訂正版 | 同一原本の再取込で二重計上せず、訂正は新版として残る |
| 7 | 売上集計と品質 | 日別・商品別・時間帯別、D/P/T差額、要確認画面 | 不一致は自動補正せず、根拠原本へ戻れる |
| 8 | ダッシュボードと出力 | 基本経営画面、CSV/Excel初版、出力履歴 | 確定値だけを出力し、値・状態・版を表示 |
| 9 | 運用保全 | 監査ログ、復元手順、バックアップ証跡、端末テスト | 匿名化データで復元に成功し、iPhone/PCの主要操作を確認 |
| 10 | OCR・提案の段階導入 | OCRアダプター、AI提案・SNS案の隔離機能 | 送信先、費用、再実行、引用データ、利用者承認を記録。業務確定と分離 |

各PRは1つの目的に限定する。DB変更を含むPRには、マイグレーション、RLSテスト、ロールバック方針、影響する画面を必須とする。

## 最初に実装すべき最小PR

最初の実装PRは、つばさ1の業務画面を変えない「PR 1: 開発の安全網」である。

内容は次だけに限定する。

- GitHub Actionsで `pnpm install --frozen-lockfile`、`pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm build` を実行
- 秘密情報、`.env.local`、画像、Excel、PDFの誤登録を検査
- 実データや本番環境へ接続しないテスト用環境を明記
- PRテンプレートに「実行した検証」「未検証」「DB変更」「データ影響」を追加

このPRは認証、RLS、OCR、実データを変更しない。以後の作業で、以前のような依存関係崩れや未検証変更が混入するのを防ぐ。

## 実装時の重要設計

### 店舗分離と認証

- 全業務テーブルに `organization_id` または `store_id` を持たせる
- RLSは `auth.uid()` と `store_members` を必ず組み合わせる
- APIでもログイン状態・権限・対象店舗を検査する
- サービスロールキーはユーザーリクエストの代行に使わない
- 匿名アクセスは作らない

### 原本と確定値

- 原本はStorageの追記専用キーへ保存し、DBにSHA-256とメタデータを残す
- OCR結果、手入力、確認値、確定値を同じ列で上書きしない
- 確定後の訂正は新しい版を追加し、旧版・理由・根拠・操作者を残す
- 不明値や不一致は要確認として残し、AIが数値を補完しない

### OCRとAI

- 原本登録が先、OCRは後
- 1回の操作で複数の外部AIへ画像を送らない
- OCRは候補値だけを作り、確認者が承認するまで集計へ反映しない
- 外部送信する場合は店舗の同意、送信先、モデル、費用、実行者、時刻を記録
- AI経営提案とSNS投稿案は、確定済み・権限のある集計データだけを読む

### テストと公開

- 実データ、実画像、実通帳、給与明細をテストに使わない
- 単体・結合・RLS・API・UI・復元の各テストを分ける
- 本番公開前に、テスト店舗と匿名化データで取込から確定、訂正、出力、復元を通す
- テストできなかった項目は、リリースノートと画面に未対応として表示する

## 加来さんにお願いする操作

この段階では不要である。監査・計画・AI作業規則はAI側で作成する。

PR 3以降、実Supabaseを作る時だけ次の判断が必要になる。

1. つばさ2専用のSupabaseプロジェクトを新規に作ることの承認
2. 所有者アカウントに使うメールアドレス
3. OCRを外部送信してよいか、ローカル優先にするか
4. 原本・監査ログ・バックアップの保存期間
5. 店舗ごとの利用者ロールの運用方針

APIキー、サービスロールキー、実画像、通帳画像をチャットやGitHubへ貼り付ける必要はない。

## AI側で実行する操作

- 新規リポジトリ、テスト用データ、CI、マイグレーション、画面、API、テストの作成
- つばさ1からの安全なコード・設計の選択的移植
- SQL、RLS、型、API、画面、計算ロジックの相互検証
- PRごとのビルド、Lint、型検査、テスト、変更影響の報告
- 実データを使わないE2E・復元リハーサル
- セキュリティ上の問題と未確認事項の継続記録

AIは、実サービスの契約、実本番DBへのマイグレーション、実データのアップロード、公開、外部AIへの原本送信を、明示承認なしに行わない。
